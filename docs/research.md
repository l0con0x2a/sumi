# 調査と設計判断

SKK の操作と辞書形式は、既存実装の規則とテストを参照して決めています。
エディタの内部構造は持ち込まず、入力状態、辞書、保存、呼出元の責務を分けました。
完全互換を主張するものではなく、確認した範囲は自動テストと制約の説明に残しています。

### 入力モードとローマ字

入力モードと、直接入力、読み、候補選択の段階を別々に扱います。
ローマ字変換では未確定の接頭辞を保持し、かなとして完成した部分だけを返します。
促音では後続の子音を残し、n は後続文字や確定操作に応じて処理します。

調査した標準表は、`nn` を直ちに「ん」に確定します。
sumi の Engine とセッションも、これを既定にしました。
一般的なローマ字入力として `konnichiha` を使う場合は `common` を選び、後半の n を次の母音まで保留します。
辞書を使わない `kana` フィルタではこちらを既定にし、大文字や `q`、`l` を SKK のコマンドとして解釈しません。

キーの役割は、単に文字名だけでは決められません。
たとえば `l` は ASCII モードへの切替ですが、`zl` は矢印の入力です。
変換表の一致を優先し、モード切替の際は末尾の n を確定して、未完成の子音を破棄します。
これらを `tests/compatibility.rs` に記録しました。

### 読みと送り仮名

大文字で読みの入力を始め、読みの途中の大文字で送り仮名を始めます。
ただし、未確定の音節を完成させる大文字は語幹に含めます。
たとえば `N A` は「な」で、`KanJ i` は語幹「かん」、送りキー j、送り仮名「じ」です。
送り仮名のかなが完成したら、Space を待たずに検索します。

候補選択中も元の読みを保持し、取消しや最初の候補からの `x` で読みへ戻れます。
通常文字を続けた場合は現在候補を確定し、その文字を再処理します。
候補末尾からの入れ子の登録は実装せず、端末 UI では読みへ戻って Ctrl-R で登録する構成にしました。

### 辞書と学習

見出し語、候補本文、注釈、送り仮名ブロックを分けます。
送り仮名ブロックは、同じ辞書内で該当する送りの候補を優先する情報として使います。
複数辞書では上位辞書を先に評価する順序を保ち、下位辞書のヒントが上位辞書の一般候補を追い越さないようにしています。

辞書中の `(concat "...")` は、文字列の表現としてだけ復号します。
任意の Lisp 式や外部コマンドを評価しません。
学習は候補順と送りブロックを更新する処理として Engine の外に置き、保存先を明示した場合だけファイルへ反映します。

ユーザー辞書を保存する際は、未対応データを黙って落とさないように検証します。
ファイル保存の設計と、複数セッションの更新の扱いは [アーキテクチャ](architecture.md) を参照してください。

## テストへの反映

skkeleton の preedit テストでは、表示の差分や書記素の扱いを確認しました。
sumi の Engine は表示済み本文を削除せず、確定差分と未確定全体を返します。
確定後の本文の結合文字編集は端末 UI の責務にしました。

skk.nvim の session テストでは、pending を優先した Backspace、UTF-8 の読み削除、送り境界などを確認しました。
libskk のテストでは、未確定の子音、n の確定、促音、句点、モード切替、送りあり変換を確認しました。
これらを観点として独自のテストを書き、上流テストのコードや全テスト群は移植していません。
上流実装を同時に動かす完全な差分テストは未実施です。

未対応の半角カナ、全角英数、abbrev、数値変換、入れ子登録などは、既定動作に見せかけず制約として残しています。
現在の対応範囲は [README](../README.md)、測定とテスト環境は [検証記録](validation.md) に記載しています。

## 言語選定

|基準|Rust（採用）|C|Haskell|
|---|---|---|---|
|状態機械|enum と match で状態と付随データをまとめられる|tagged union と手動の不変条件管理が必要|代数的データ型と純粋関数で表現しやすい|
|UTF-8|String の境界検査と文字イテレータを利用できる|文字境界とメモリ管理を自前で扱う|Text と文字列型の使い分けが必要|
|入力遅延|GC なし。今回の実装を測定できた|メモリと処理を直接制御できる|GC とランタイムの影響を別途測定する必要がある|
|CLI と配布|単一バイナリ、Cargo、少数の依存|小さく実装できるが JSON 等の実装選定が必要|GHC と依存、ランタイムを含む配布を別途評価する必要がある|
|テストと保守|組込みテスト、所有権、型検査を利用できる|テスト基盤とメモリ検証を追加する必要がある|純粋な状態遷移のテストに適する|

Haskell や C で同じ処理を実装して性能比較したわけではありません。
今回の状態表現、少数依存、Void Linux での配布と保守の条件から、第一候補の Rust を採用しました。
Rust 1.89 と stable でテストし、glibc 版と musl 静的リンク版を確認しています。
